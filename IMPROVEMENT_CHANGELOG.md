# Improvement Changelog

This file tracks the evolution from a simple review baseline to the final ChangeGuard workflow. Submission metrics are generated by the fixed benchmark; no hand-entered score is treated as evidence.

| Stage | What changed | Why | Result / decision |
|---|---|---|---|
| Baseline | Same-model single-prompt reviewer | Establish a fair starting point without agentic orchestration | Keep as the official comparison baseline |
| Iteration 1 | Deterministic infrastructure rules | Catch explicit high-confidence IaC failure modes without model variance | Kept for precision and reproducibility |
| Iteration 2 | Structured GitHub PR ingestion and bounded diff parsing | Replace free-form context with exact changed-file evidence | Kept; every analysis now has reproducible inputs |
| Iteration 3 | LLM Risk Agent | Detect semantic risks not covered by static patterns | Kept only as a hypothesis generator |
| Iteration 4 | Exact evidence verifier | Stop unsupported AI claims from influencing consequential decisions | Kept; unmatched claims become explicit rejected artifacts |
| Iteration 5 | Persistent trajectories, reports and benchmark exports | Make the workflow auditable and reproducible by judges | Kept; outputs can be exported directly from stored runs |
| Iteration 6 | Separate evidence provenance from decision authority | An exact quote proves where a claim came from, but does not by itself prove that a benign change is hazardous | LLM-only low/medium findings are advisory; high/critical LLM-only findings require human review instead of autonomous BLOCK |
| Iteration 7 | Normalize removed-line matching before deterministic evaluation | Kubernetes field names such as `readinessProbe` were being compared with mixed casing | Fixed readiness-probe removal detection without changing the benchmark data |
| Final | Evidence-backed PASS/WARN/BLOCK + GitHub review write-back | Deliver an end-to-end user workflow rather than an AI draft | Final workflow used in the official benchmark |

## Measured benchmark progression

The benchmark dataset was not changed between these runs. Both baseline and ChangeGuard used **GPT-5.6 Luna** on the same fixed 15 cases.

### First real run

- Baseline decision accuracy: **87%**
- ChangeGuard decision accuracy: **87%**
- Improvement: **0 percentage points**
- Danger detection: **100% → 100%**
- Safe-change accuracy: **80% → 80%**

The run exposed two concrete defects:

1. `k8s-readiness-removed` was downgraded to WARN because the deterministic removed-line check compared the mixed-case Kubernetes field name incorrectly.
2. `safe-timeout-small` became a false WARN because a quote-verified medium-severity LLM hypothesis was treated as decision evidence even though no deterministic risk corroborated it.

### Final measured run

After fixing those two architectural issues and rerunning the **same dataset with the same model**:

- Baseline decision accuracy: **87%**
- ChangeGuard decision accuracy: **100%**
- Improvement: **+13 percentage points**
- Danger detection: **100% → 100%**
- Safe-change accuracy: **80% → 100%**
- Baseline token usage: **2,964 tokens**
- ChangeGuard token usage: **4,792 tokens**
- Evidence-linked AI claims: **13**
- Rejected unmatched AI claims: **0**

The final workflow correctly classified all 15 cases, including both designated challenging cases.

## Removed / constrained experiment

### Unverified free-form LLM review

An unconstrained reviewer was intentionally rejected as the final architecture. It could produce plausible statements about dependencies, runtime behavior or blast radius that were absent from the submitted change.

The final system requires an AI risk to identify a file and quote exact evidence from its patch. If the verifier cannot locate the quote, that claim is marked **REJECTED**. Even when the quote is present, provenance verification is not treated as semantic proof: low/medium LLM-only findings remain advisory, while high/critical LLM-only findings require human review rather than autonomously blocking a change.

### Why not simply give the model more repository context?

More context increased the surface area for plausible inference without guaranteeing proof. ChangeGuard therefore prefers bounded evidence and explicit tool results over silently expanding context.

## Evaluation protocol

The official benchmark contains 15 labeled infrastructure-change cases, including deliberately challenging cases. Baseline and ChangeGuard use the **same configured LLM model**. The main difference is the workflow around that model.

Primary metric: **decision accuracy against fixed ground truth**.

Secondary metrics include danger detection, safe-change accuracy, evidence-linked/rejected AI claims and token usage.

See [`docs/BENCHMARK_PROTOCOL.md`](docs/BENCHMARK_PROTOCOL.md).

## Hot take

> More model freedom did not make the reviewer more trustworthy. Reliability improved when the model was treated as a hypothesis generator, evidence provenance was verified independently, and the final gate required stronger evidence than a plausible model interpretation alone.
